Migration plan · Model C into the live library

Rename the tokens we have. Don’t rebuild them.

How to move the live SKO library to the Model C colour roles with the least work, using what the test file proved. Every number below was measured on 19 Sep 2026 in the live DS file and in LMS ICP Phase 1, the main file that consumes it.

Status steps 1–8 applied 19–21 Sep; Skins and 113 legacy tokens deleted; ICP clean; published 22 Sep; roles renamed element-first 22 Sep Rehearsed in ❖ SKO Design System (OptionC-Material) Applies to ❖ SKO Design System (Untitled UI)

In one minute

Renamed again, 22 Sep

The roles this migration created now carry element-first names (bg/page, text/default, border/subtle…): same variables, same colours. The steps below keep the names of their day; the colour memo §0 maps each one.

The recommendation

Rename in place. 42 of the 43 roles already exist in 1. Semantics under their current SKO names, with the exact Light and Dark value. For example, SKO/Colors/Background/bg-primary becomes surface. Each one takes the new name and keeps every binding. Only on-primary-hover is new.

Why not a new collection

Every consumer would have to re-bind. ICP alone: 13,623 direct bindings and about 735 frames that force a mode. The DS itself has 1,317 forced modes, the regression that broke the dark Topbar in the test file.

What it costs

One scripted session in the DS file, in ten steps, with a named version before each. Then you publish and consumers accept the update. Nothing to re-bind downstream.

What changes on screen

No token changes value: all 411 old variables resolve to the same SKO Light and SKO Dark colours as before. What changes comes from the fixes replayed from the test file: text on primary buttons, the hover pair, the pressed toggle, the mobile footer and the Course-Completed button.

Where it stands

Applied 19 Sep, steps 1 to 7, in order 1, 2, 5, 3, 4, 6, 7. A first attempt was rolled back because its checker read same-collection aliases in Light only. The redo stored every raw value first and checked each role against its true Light and Dark pair, alpha included. All 42 survivors and 47 planned aliases matched the plan.

3What stays as legacy, and why

  • 298 variables in use have no matching role. Most are the Untitled UI palette inside the base components (Buttons, Badges, Inputs, icons), with 238,606 bindings between them. They stay working and hidden from the picker. Mapping them would shift shades, which is a design decision.
  • 43 of them are SKO-named and worth a look later: text-brand-tertiary (3,421), border-tertiary (2,125), Icon/default (1,433), bg-active (1,002), focus-ring (423), and the Untitled UI shadow scale.
  • Nothing is deleted in steps 0 to 9. Deletion is step 10, with a check of every consumer first.

4What the test file taught us

  • A forced mode only belongs to its own collection. Moving bindings to a new collection left the dark Topbar and 14 demos rendering light. Renaming in place avoids this entirely.
  • A new mode starts from the default mode’s values. That is why step 2 comes straight after step 1.
  • A second fill’s opacity doesn’t reach instances. The toggle’s state layer is a separate layer with its own opacity.
  • Compare colours with their alpha. scrim and shadow are translucent, and a check without alpha reports false changes.
  • Scripts run in batches of 20 to 25 seconds. The live file is large, and the plugin stops a call at 30.
