Which colour token model do we ship?

The design team raised a fair question: are our colour names too many and too specific? We measured it, compared three models, and recommend one.

Status decided: Model C, live since 19 Sep; renamed element-first 22 Sep (same colours, new names, §0); engineering answers 21 Sep Revised 23 Sep 2026 In Figma Colour token model · decision memo, frames 08–13

In one minute

The question

Keep role-by-element names (A), go flat with primary · secondary · tertiary (B), or adopt Material-style roles (C)?

What we measured

98 colour tokens resolve to 42 values. 80 of them share a value with another token, and one colour carries six names.

Adopted: C (19 Sep), renamed 22 Sep

Since 22 Sep the roles carry element-first names (bg/page, text/default, border/subtle…), 83 tokens in all; §0 maps every name. What follows was written with the Model C names. 47 roles with on- pairs in the live library (the proposal started from 27 core roles), plus 16 accents. The same words in CSS, React Native and Flutter, so nobody keeps a mapping table.

Why not B

Flat names have no on- pairs. Dark mode and text-on-surface get decided in code, separately on every platform.

What it costs

One rename of about 100 tokens. The old --sk-* names stay alive as aliases, so there is no flag day.

What we need from you

Engineering answered the first round on 21 Sep (no Tailwind in SKO; Storybook stays the component layer). Still open: who owns token approvals, the --sk-* date and the mobile stack. None of them changes the recommendation.

2Why C

  • The mapping has to live somewhere. The cheapest place is the token name. “Designers keep it simple, developers map” is the same work done three times, by hand, where nobody compares it.
  • One vocabulary across platforms. Flutter’s ColorScheme and React Native Paper’s MD3 theme use these slots word for word; on the web they are plain CSS variables, which work with any styling approach.
  • It is design vocabulary, not framework jargon. surface, on-surface, primary, outline, error. The frameworks adopted it, not the other way round.
  • Simpler for designers. From 411 semantic tokens, 283 of them hidden, to 47 roles in a picker grouped by role (27 in the first proposal).
  • Dark and brands become a theme swap, never a branch inside a component, because the text colour comes with the surface.

3The set, in short

  • Surfaces: three tiers, not five, each with its on- text.
  • Brand: primary · on-primary · primary-container · on-primary-container. No tertiary; secondary is optional.
  • Lines: outline and outline-variant.
  • Feedback: error, success, warning, info, each as a pair.
  • Accents: teal, green, red, yellow, in the same shape: accent-teal · on-accent-teal · accent-teal-container · on-accent-teal-container. Sixteen tokens, SkillUp brand colours. Proposed for screens only; since 23 Sep not restricted, in screens and components, until daily use decides the rule.

4How design and code stay in sync

Three lanes, left to right. Values only ever move that way.

Lane 1 · Design

Figma

The designer changes a token or a component and publishes the library. Nothing else.

Lane 2 · The bridge

One tokens file, one pull request

The Figma variables are exported to one tokens file in the repo Storybook builds from, and the change arrives as a normal pull request. Storybook shows it before merge; one named engineer approves. The same file is then written in each platform’s spelling. The export can start by hand and be automated later.

Lane 3 · Code

Web · Mobile · Marketing

Each product installs the new version when it is ready. Components show up in Storybook, the common layer where Design and Development review them together.

↩  Only one thing travels back: visibility. Each component carries its own code snippet and a link to its Storybook story, both visible in Dev Mode. A value never comes back.

We do not have Code Connect. It needs Figma’s Organization plan, and so does file branching. Its job is done by two fields every plan has: the component’s description carries the code snippet, and its documentation link points at the Storybook story. Both appear in Dev Mode exactly where Code Connect would, and both are written by script from the component name and its properties. That makes the naming convention the bridge, which is an argument for it, not against it. Proved on 89 components in the Model C test file.

Three kinds of change

A value changes

The tokens file changes in a pull request, the token owner approves after checking Storybook, nothing else changes. The everyday case.

A token is added or renamed

The old name stays as an alias with a retirement date. Components migrate repo by repo.

A component changes

A normal ticket: implement from Dev Mode, add the Storybook story, update the component’s snippet and link.

5Modes and the ten-per-collection limit

Decided 18 Sep: there is no separate Brand collection. Each brand is a pair of modes in 🎨 SKO-Semantics, Light and Dark, so the official tokens live in one collection. Figma allows ten modes per collection on our licence, so five brands is the ceiling. We start with three: SKO, Gold and Red. Two slots stay free.

Partners are not brands. Five partners would not fit, so a partner gets a token pair, partner-x and on-partner-x, used by the Provider Badge. It costs no modes.

A brand colour must never read as a status colour. One rule for every brand role: the nearest step of the brand’s own ramp that sits at least 10 ΔE (perceptual distance) from every error and warning colour in the same mode, with text at 4.5:1 or better on it, and the outline at least 10 ΔE from its container so the border stays visible. Before the rule, Red Light primary was the exact value of on-error-container and Gold Dark the exact value of warning. Progress stays blue in every brand; it is info, not primary.

Hover. The primary button keeps SKO’s yellow hover through a Material-shaped pair, primary-hover and on-primary-hover, the same shape as success and warning. It is for the primary button only; every other hover uses Material’s state layer, the on-colour at 8% over the fill, so no role needs its own hover token. The pressed toggle is the first case: its track stays primary and a layer named state-layer, filled with on-primary at 8% opacity, sits under the knob. In Figma that has to be a separate layer with its own opacity, not a second fill on the track: instances do not inherit the opacity of an added fill. Hover is exempt from the 10 ΔE rule: it only shows under the cursor, on something already labelled as a button, so nobody reads it as a warning. Its own rule: it always lightens, as SKO’s does, and sits at least 10 ΔE from the button and from primary-container, with text at 4.5:1 or better. The pair also fixes Dark mode, where the live DS puts #CDEAF6 text on #6CC0E0, 1.6:1; it is now #0E1A1F, 8.6:1.

Text on a brand fill is always on-primary, never a fixed white. The button’s default text was bound to white in every mode, which fails in Dark once the brand fill is light: SKO 2.9:1, Gold 1.4:1, Red 2.3:1. With on-primary, white in Light and #0E1A1F in Dark, it is 6.2, 12.3 and 7.7:1. This is exactly what the on- pairs are for.

Fixed surfaces, added 21 Sep. Three roles for a surface that must stay light in Dark and in every brand, named on Material’s *-fixed pattern: surface-fixed #FFFFFF, surface-fixed-dim #F8F9FA and on-surface-fixed #13282F, the same in all six modes. The text role is not optional: on a surface that stays white, on-surface would turn light in Dark and vanish, while on-surface-fixed keeps 15.3:1. First use: the icon circle in the Topic Types badge, which sat on the legacy bg-secondary_alt; that token is now an alias of surface-fixed-dim. The rule stands: no new role without the team’s approval, and every name follows Material.

Focus-ring gap, added 22 Sep. The focus rings draw two shadows: a thin gap around the element, then the coloured ring (primary, error or success). The gap sat on the legacy bg-primary. Moving it to surface would have changed Dark from #062C41 to #0E1A1F, so the team chose a role of its own, focus-ring-gap: #FFFFFF in Light, #062C41 in Dark, the same in every brand, scoped to effect colours only. The eight focus-ring effect styles use it and nothing else does.

Only the seven brand roles change per brand; the other 40 roles copy SKO. Closest brand-to-status pair left: ΔE 10.2, Red Light primary-container. The cost: Gold and Red containers are more saturated than SKO’s near-white. Paler ones would need new primitives with a shifted hue.

6Questions for the developers

Answered by engineering, 21 Sep (Vikas Goyal). SKO does not use Tailwind. It was an example, never a requirement: the tokens ship as plain CSS variables such as var(--color-on-surface), which SCSS, CSS-in-JS, PHP templates and Storybook all read. Storybook stays the component layer. It renders and documents components but does not hold their values; those live in a theme or variables file in the repo, and a token pull request is simply how that file changes, so Figma and code stop drifting (47 roles × 6 modes is about 280 values, too many to copy by hand). “PR approval owner” only means agreeing who reviews and merges: one named engineer for tokens, the component’s owner plus a design sign-off in Storybook for components, and a version number with a changelog.

  1. Web styling today: SCSS, CSS-in-JS or a UI library? The CSS variables work with all three; the answer only sets the output format.
  2. Material names verbatim? Any objection, and to a theme extension for success, warning, info and accents?
  3. Token owner: who on engineering approves token pull requests?
  4. What does marketing consume: PHP templates reading the CSS variables, or values baked in?
  5. How long do the --sk-* aliases live? A date.
  6. Accent names in code: the hue, accentTeal, or a brand name?
  7. Mobile App stack: React Native with Paper, with NativeWind, or its own theme object?

Settled: no Tailwind and no shadcn alias layer, since neither is used in SKO. For the Head of Development: whether the export stays manual or is automated later.

Flutter is the deciding row

Flutter’s ColorScheme is the Material 3 vocabulary, word for word: primary, onPrimary, primaryContainer, surface, onSurface, surfaceContainerHighest, outline, error. If the Figma tokens carry those names, the Dart theme is a direct copy. success, warning and info come in as a ThemeExtension, which is the official mechanism for exactly that.

React Native: the same answer, one row down

React Native has no CSS and no CSS custom properties. A theme is a plain JavaScript object, theme.colors, handed to a ThemeProvider; Light and Dark are two objects swapped on useColorScheme(), and a brand is simply another pair of objects. An object accepts any key, so B and C both run. The difference is how much of the design lands in component code.

Flutter’s ColorScheme and React Native Paper’s MD3LightTheme.colors are the same Material 3 slots; a Paper app takes the C names verbatim, a NativeWind or custom-theme app takes them as an object, and in every case the on- pairs keep Dark and the brands out of component code. Tailwind is a consumer, not a fourth model

Tailwind’s built-in palette, slate-900, blue-500, is value-naming: the primitives layer we are hiding from designers. On its own it has no primary or surface; teams add those on top, and that is what the LMS prototype already does today with --sk-* variables mapped to bg-sk-* utilities. Any of the three models feeds it: v3 through theme.extend.colors, v4 through @theme { --color-* }, where every declared variable becomes a utility with no configuration.

The most common Tailwind semantic layer is shadcn/ui, and it is the C model with different words: -foreground is Material’s on-.

Where the flat model breaks
  • No contrast pair. Text on primary has no token of its own, so a designer picks background, which is white. It works in Light. In Dark, background goes near-black and the text disappears. Every flat system that shipped Dark mode grew pairs afterwards: Bootstrap 5.3 added -text-emphasis and -bg-subtle for exactly this reason. B is not stable; under pressure it becomes C.
  • The decision moves into code, on every platform. With secondary as the only name, the React developer decides it is the card border, the Flutter developer decides it is supporting text, and neither is wrong. The duplication has not gone away; it has moved from tokens into three codebases, where it drifts without anyone noticing.
  • The short-picker advantage disappears with scopes. The short list is B’s strongest argument. But Figma variable scopes, already step 3 of the plan and free to set, do the same for A and C: someone colouring text sees only the text tokens. After that, B is not shorter where it counts.

The rebrand argument does not separate the models. When the brand changes, what gets edited is that brand’s SKO-Semantics modes and the primitives; the semantic layer aliases through and is not touched. That holds with 12 tokens or with 80. Rebrand cost is the same in A, B and C.

Who owns the mapping? The full argument and the ten-minute test

Bruno and Navdeep keep asking a fair question: whatever model we pick, why should the design system carry a developer-shaped scheme at all? Why not give designers the simplest possible names and let each codebase map them on its side?

Because the mapping has to live somewhere, and the cheapest place for it is the token name in Figma. “Designers keep it simple, developers map on their side” is not the lighter option; it is the same work done three times, by hand, where nobody compares it.

  • If developers map, they map three times. Web (CSS), Mobile App (React Native) and marketing (PHP) each keep a hand-written table, owned by different people, that nobody diffs. That is exactly what we measured in the current file: 98 tokens for 42 values, and the same decision taken differently on each side. Moving the problem does not remove it.
  • Every colour in the handoff gains a step. In Dev Mode the developer reads the token name and types it. If Figma says text/muted and the code says onSurfaceVariant, every binding is a lookup. The sidebar we re-cut this week has about 300 bindings.
  • A single scheme is not “developer-oriented”. surface, on-surface, primary, on-primary, outline, error are Material’s design vocabulary. Flutter, React Native Paper and shadcn adopted it because it is how designers already talk about colour, not the other way round. Model C does not bend the tokens to a framework; the frameworks bent to the tokens.
  • The simplification for designers is this vocabulary. From 411 semantic tokens, 283 of them hidden, to 47 roles in a picker grouped by role (27 in the first proposal), plus the 16 accents for controlled freedom. Designers do not get harder names; they get far fewer.
  • What developers do is not mapping, it is transformation. Style Dictionary writes --color-on-surface for the web, onSurface into the React Native tokens.ts and the Paper slot. That is a spelling rule, run by a build, not a table of decisions kept by a person.
OptionTodayIn a year

The cost of C is paid once, at the rename, and §8 already keeps the --sk-* aliases alive so there is no flag day. The cost of the other option is paid on every handoff and again on every new platform.

A ten-minute test to settle it in the meeting. Take the sidebar we re-cut this week. With C names the developer reads on-surface-variant in Dev Mode and types text-on-surface-variant. With designer-only names they read text/muted, open the table, find onSurfaceVariant, type it. Now imagine that 300 times for one screen.

Modes and the ten-per-collection limit, in detail

Our Figma plan allows ten modes per collection. The model choice does not touch that number: in A, B and C alike, semantic colour lives in one collection with two modes, Light and Dark. What differs between the models is how many tokens sit inside it, 70, 12 or 27, never how many modes.

That is what the one-axis-per-collection rule buys. The limit is per collection, no collection carries two axes, so nothing multiplies:

CollectionModes todayHeadroom
🎨 SKO-Semantics6 · SKO, Gold, Red, each Light and Dark4, so two more brands
📐 Layout3 · Desktop, Tablet, Mobile7

The only pressure point is SKO-Semantics, because brands are its modes: two per brand, ten per collection, so five brands is the ceiling. Measured on the LMS page on 15 Sep: zero nodes set a brand explicitly; every screen renders in SKO.

Decided 18 Sep, replacing the 15 Sep partner-skin decision. The Brand collection is gone; brands are modes of 🎨 SKO-Semantics, SKO, Gold and Red today, five at most. Violet, Sky and Ink are dropped. Partners do not take brand slots: each is a token pair, partner-x and on-partner-x, in Colour, zero modes.

For Flutter, a Brand mode is a ColorScheme instance, and a Provider Badge that shows IBM beside Microsoft on one screen is the same thing it is in Figma: a per-instance override, a local Theme wrapping the widget with that partner’s scheme. Nothing new to build.

Fixed 19 Sep: fixed-white on brand fills became on-primary — the Progression button label and icons, and the pressed toggle knob, which is Material’s selected handle colour. The Course-Completed button now pairs success with on-success: its label was 1.7:1 in Dark, now 5.1:1, and its fill no longer borrows a text role. The mobile footer’s inactive tab moved from on-warning to on-surface and its background from fixed-white to surface, so the footer follows Dark instead of staying white. The Topbar Theme=Dark and 14 dark or light demo frames forced a mode only on the old Semantics collection, so after the migration they rendered light; they now force SKO Dark or SKO Light on Colour too. Limit this exposes: a component that forces Dark must also pick a brand, so the dark Topbar is always SKO; moving the Topbar to modes (Plan step 7) removes that. Still to review: warning and on-warning are bound by no component yet.
