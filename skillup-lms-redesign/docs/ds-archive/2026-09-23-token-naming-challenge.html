Second opinion · for design and engineering

Did we pick the right token naming strategy?

Model C went live on 19 September. Before the team builds on it, this document tests the decision against what the most respected design systems and their authors actually do, audits all 47 roles, and says what to change and what to leave alone.

Status challenge, not a decision · outcome 22 Sep: element-first chosen and applied Written 22 Sep 2026 Scope colour roles, token structure, type and spacing names Evidence 11 production systems, 12 authors, 2 industry reports, the live library

In one minute

Outcome, 22 Sep

After this challenge Nelson chose element-first names, with the word primary kept. They were applied to the live library the same evening: 47 roles renamed, 20 tokens added to split roles by element, 16 accents, published and re-bound in ICP. The Rename impact doc measured the cost; the colour memo §0 maps every name. This page stays as the reasoning.

Structure · sound

Tokens born in Foundations only, primitives hidden, a semantic layer and no component tier yet, role-not-value names, one canonical name transformed per platform, aliases with a retirement date. This is what 85–90% of systems do and what every author we read recommends.

Vocabulary · defensible, premise weakened

Material names were chosen so that a framework reads them by name. Today no confirmed platform does: the web is plain CSS variables with no Tailwind and no Material UI, and the mobile stack is still question 7.

43% of the set is not Material

Of 47 roles, 19 are Material verbatim, 8 follow its shape, 20 are SKO inventions in Material dress. Flutter or Paper would take 19 slots directly and need an extension for the rest, so "no mapping table" was never fully true.

What the best systems do

Atlassian, Polaris, Carbon, Primer, Spectrum, Apple and Figma's own guide name by element first (text, background, border) and still carry contrast pairs. Material and shadcn name by role first. Both camps are respectable; the element-first camp is larger.

Six defects to fix now

surface-variant is deprecated by Material and duplicates a value; three border roles are named as containers; fixed-white encodes a value; info has no pair; primary-text is justified by a contrast need the numbers do not show; the picker is a flat list of 47. All are renames that keep bindings.

Recommendation

Keep Model C. Do not rename the vocabulary twice in one week without evidence. Apply the six fixes, write down the decision test that ends the debate, and set two conditions that would reopen it, at most once.

Role first

Material, shadcn, Flutter, Compose, RN Paper, Angular Material
  • Strength: every fill ships with its text colour, so Dark mode and brands are a theme swap and never a branch in a component.
  • Strength: the vocabulary is published, taught and recognised, and four frameworks read it verbatim.
  • Cost: on-surface-variant for "secondary text" asks the reader to know the system. Material's answer is a generator, an algorithm that fills the roles, which we do not use.
  • Cost: the set was designed around Google's tonal palettes; a brand that starts from its own palette ends up inventing roles, as we did.

Element first

Atlassian, Polaris, Carbon, Primer, Spectrum, Apple, Helios, Figma's guide, Curtis
  • Strength: the name says where it goes. Carbon renamed its whole set in v11 for one reason: so people could apply colour without opening the guide.
  • Strength: the Figma picker groups by slash, so text/…, bg/…, border/… become folders for free. Our base kit, Untitled UI, is built this way.
  • Not a weakness: contrast pairs exist here too, as a modifier: fgColor-onEmphasis, color.text.inverse, text-on-color. The memo's table called them "implicit" in Model A; in the field they are explicit.
  • Cost: no framework reads these names; the theme is always hand-mapped, which on a plain-CSS web is no cost at all.

Where the authors agree, and our plan already complies

  • One canonical name, transformed per platform. Improta's mistake #4, Atlassian's Figma-to-code rule, Figma's Dev Mode conversion. Never a second vocabulary maintained by hand.
  • Name the role, never the value. Improta's mistake #2, Curtis, Figma: "A token named text-secondary will outlast a rebrand."
  • Two tiers first, a component tier only when a component must diverge. zeroheight's 2026 report: 90% primitives, 85% semantic, 52% component. Nate Baldwin, who built Spectrum's component tokens, warns a single component can spawn 432 of them.
  • Do not globalise early. Curtis: three real uses make a value token-worthy; before that it stays local. Our new-token rule should carry that threshold.
  • Rename with aliases and a retirement date. Improta's mistake #6. We have _legacy/ and --sk-*; we still owe the date.
  • Consistency over preference. Curtis on on- versus alternatives: the choice tilts to taste; that a convention exists matters more. Stuart Robson: the best naming system is the one the whole team actually follows.

2The premise, checked

The rule agreed on 17 September was: adopt Material's names only where a framework on the other end reads them by name. Here is who reads them today.

PlatformReads Material names by name?Status on 22 Sep
Web · SKO LMSNo. Plain CSS variables in the Storybook repo. No Tailwind, no Material UI. Any name works.confirmed 21 Sep
Marketing · PHP / HTMLNo. The same CSS variables.confirmed
Mobile · FlutterYes. ColorScheme takes 19 of our 47 roles verbatim; the other 28 go through a ThemeExtension.not chosen
Mobile · React Native + PaperYes. The MD3 theme object, same 19 / 28 split.not chosen
Mobile · React Native, own theme or NativeWindNo. A theme is a JavaScript object; any key works.not chosen
LMS prototype · TailwindNo. Utilities are generated from any name.comparison only

So the premise is a bet on the mobile stack. If question 7 comes back "Flutter" or "Paper", the bet pays 19 slots and a familiar vocabulary for the mobile team. If it comes back "React Native with our own theme", the Material names carry only their intrinsic merits: the on- pairs, a published spec, wide recognition. Those merits are real, but the element-first camp has the pairs too, and the recognition cuts both ways: a Flutter developer who knows Material will expect surface-variant to be deprecated and on-surface-muted not to exist.

5The question Bruno and Navdeep keep asking

Why should the design system carry a developer-oriented scheme at all? Why not let designers pick simple names and let each codebase map them?

The field's answer to the second half is unanimous: no. Every system in section 1 uses one vocabulary in Figma and in code. Atlassian's Figma names and code names are the same words in different casing; Figma's Dev Mode turns color/action/primary into --color-action-primary and expects developers to type exactly that; Gordashko's rule is that the transform may add prefixes and change casing, never meaning; Improta lists a hand-kept mapping as a mistake. Per-codebase maps are what teams abandoned with the CTI era. The memo's ten-minute test stands.

But the first half deserves a better answer than the one we gave. "Simple for designers" is not the same as "Material". The field's simple-for-designers answer is element-first semantic names, text/secondary, bg/brand, border/subtle, exported unchanged. Carbon did its v11 rename for exactly that reason, and Untitled UI, the kit our whole library is built on, already speaks that way. Element-first would have been just as much "one vocabulary", arguably more legible in the picker, and free of deprecated or invented Material names. We chose role-first because of the on- pairs and a bet on the mobile stack. That is a fair choice, and it should be presented as a choice, not as the only way to keep design and code in sync.

What to tell them. The scheme is not developer-oriented; it is a shared vocabulary, and the alternative the field recognises is a different shared vocabulary, not a mapping table. We are three days past a published migration. Switching now costs credibility and about three days of work; the benefit is unmeasured. So we keep Model C, fix its defects, and agree on the test below.

6Recommendation

Keep Model C. Fix the six defects in one publish. Close the debate with a written test rather than another opinion, and name the two facts that would reopen it.

Now, one publish

  1. surface-variant: decide fold or rename (finding A). The only step with a visible change, in Dark.
  2. Three border roles → *-outline-variant (B).
  3. fixed-white → on-scrim (C).
  4. info: complete the pair or document the exception (D). Note in the memo that warning exists for symmetry.
  5. primary-text: rewrite the justification (E).
  6. Picker folders in Figma, codeSyntax unchanged (J); descriptions "use for / never for" on every role, since 30 of 47 still say only "was …".

The decision test, to write into the Plan

A naming proposal is acceptable when all four hold: one canonical name lives in Figma and is typed unchanged in code apart from casing and prefix; the name says the role, never the value or the element's current look; every fill role has a text role that goes with it; a new name is added only after three real uses and one approval. Model C passes. An element-first model would pass too. We have Model C.

Two conditions that reopen it, at most once

  • Question 7 answers "React Native with our own theme or NativeWind", so no framework reads the names, and
  • a twenty-minute picking test with three designers, on real screens, shows more than one mis-pick in five on Model C names. Run it in October, after the ICP work, and log the result in the memo either way.

Owed to engineering before the first export

  • The export splits the six modes into two modifiers, brand and scheme, in the DTCG resolver shape.
  • The transform reads codeSyntax, not the Figma path, so picker folders never reach code.
  • A retirement date for --sk-* and the _legacy/ aliases.
  • One named engineer approves token pull requests; still unnamed.
