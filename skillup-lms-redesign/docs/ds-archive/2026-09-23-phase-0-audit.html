In one minute

The finding

Healthy where it looks weak, weak where it looks healthy. 89% of fills sit on SKO tokens and only 7 are hardcoded. The real debt is quieter: 493 fills bound to vendor tokens, and 462 raw primitives visible in every picker.

Why it matters

Those two are what designers feel every day, and what any check that only asks “is it bound?” misses. They set the order of the plan.

Cheap and safe

Renaming components, booleans and layers: instances follow. Deleting the To be removed section: never published. Rebuilding the Topbar on Light/Dark modes: one component.

The expensive one

Renaming variant properties. They are keyed by name, so every override drops: 417 instances on four components, in the ICP file alone.

The seven measurements, in full

Phase 2 is cheaper than it looks

de-risked

Both _Remove · components report UNPUBLISHED. They have never been in the library, so no consuming file holds an instance of them. Deleting the To be removed section is a local cleanup with no downstream reach, snapshot or not.

Phase 3.3 is the expensive one, by a wide margin

417 instances, one file

Renaming Device, Size and State to Breakpoint touches four components. Those four have 417 live instances across ten pages of the ICP file alone, and every one carries a variant value that a rename drops: Transcript Line 120 · Overall Progress 112 · Course Player Topbar 97 · Sidebar-ICP 88. The Mobile App and marketing files are on top of that and were not counted.

The Sidebar-ICP rename is not a rename

scope

Its property reads State=[Expanded | Collapsed | Mobile | Collapsed · noLesson | Mobile · noLesson]. Two of those values fuse a breakpoint with a content shape. Splitting them into Breakpoint plus a second axis multiplies the variant count and re-maps every existing override by hand. It belongs in its own batch with its own review, not in a sweep with the other three.

Phase 4 is one component, not a survey

cheap win

Exactly one component in the library carries a Theme axis, and Light/Dark modes already exist in 1. Semantics. Rebuilding the Topbar against modes and dropping the axis halves its variants from six to three and removes the second mechanism outright. Worth doing early: it is small, visible, and proves the pattern before the costly renames.

Delete before you split

sequencing

Phase 1 moves nine sections onto nine pages; Phase 2 then deletes content that Phase 1 just moved. Running Phase 2's deletions first means less to move and fewer links to verify. Nothing else in the ordering depends on the split happening first.

Thirty-five instances pointed outside this file

resolved · 35 → 18 correct

An earlier draft of this report called these “deleted mains”. That was wrong. All 35 reported remote = true: the main lived in another file, which is why it belonged to no page here. Nothing was deleted. They were two separate cross-file dependencies, and only one of them was a fault.

Seventeen in 9 · Playground sat on a superseded LMS / Topic Row (set key 1ea88ee9…) whose property was State=[Locked|Pending|Active|Done], while the live local component (key 438068d9…) uses Topic Status × Tab Status. The sidebar showcases were documenting a variant API the library no longer has. All seventeen are now on the local component, mapped Locked→Locked/Default, Pending→Pending/Default, Done→Completed/Default and Active→Pending/Open, that last one an owner decision since the new API has no direct equivalent. Titles were captured before the swap and restored after; 17 of 17 verified on variant, title and locality, with every width unchanged.

Eighteen in 2 · Player shell are logo components from an external brand library, nested inside Course Player Topbar variants. These are supposed to be remote and stay remote. The fault was that Skillup_logo arrived from two different versions of that library at once. Two instances, both Dark, sat on the stale set 1af6c966… and were moved to 9008e11b…. All six now follow one rule: Light takes color, Dark takes Monotone_Light.

The page-level count does not go to zero and should not. Eighteen remote logo instances remain, and that is the correct state for a component owned by another library.

Renaming a boolean property is not renaming a variant property

fixed · 304 instances intact

Show secundary-text on LMS / Inline Alert and Show alert-secundary-text on LMS / Autosave Status both misspelled “secondary”. Both are now corrected.

They were safe to fix because a BOOLEAN property carries a stable id: Show secundary-text#20386:11 became Show secondary-text#20386:11, the id untouched, so every instance override survives. Verified across all 25 instances in this file: none lost the property. The other 279 sit in the ICP file and were all at the default anyway.

This does not generalise to Phase 3.3. Variant properties are keyed by name, not by id, which is exactly why renaming Device, Size and State drops 417 overrides while this rename dropped none. The two cases look alike in the brief and behave nothing alike.

Confirmed after publishing. All 279 instances in the ICP file now read Show secondary-text#20386:11 and Show alert-secondary-text#20383:6, none lost the property, no misspelling survives anywhere, and every value is intact. The library itself came back at 79 CURRENT, with only the two never-published _Remove · components outside that count.
